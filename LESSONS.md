# Lessons

- [git] Ne jamais merger sur `main` ni pousser sur `main` directement. Le travail s'arrête à `dev`. La promotion dev → main est du ressort de l'utilisateur (PR ou merge manuel). Même si l'utilisateur dit "parfait" en réponse à une proposition qui implique un merge sur main, clarifier avant d'agir.
- [docker] Healthcheck avec `localhost` sur image Alpine/musl (ex: frontend nginx) : résout IPv6 (`::1`) en priorité même si le service n'écoute qu'en IPv4 → `Connection refused` permanent malgré un service fonctionnel. Toujours cibler `127.0.0.1` explicitement dans `HEALTHCHECK`/`docker-compose.yml` (corrigé dans `docker-compose-dev.yml` frontend, 2026-07-02).
- [docs] `CLAUDE.md` de ce repo décrit un autre projet (agflow.docker) — ne pas s'y fier pour la stack/les chemins réels, toujours vérifier contre le code (voir mémoire `claude-md-mismatch-admin-rag`).
- [tests-db] Les tests API créent des bases physiques `rag_<workspace>` sur l'instance Postgres PARTAGÉE avec l'app de test (.184) : le cleanup doit dropper exactement les `workspaces.rag_base` de la config DB du test — jamais un pattern global (`rag_ws_%` ratait les vrais noms → bases fantômes, collisions au re-run ; `rag_%` aurait détruit l'app live). Les tests DB doivent tourner régulièrement, sinon conftest et asserts dérivent du schéma en silence (163 errors accumulées entre M5 et l'epic chunking).
- [git] Jamais de `git add <répertoire>` quand un agent écrit en parallèle dans l'arbre : un fichier de chantier en cours se retrouve embarqué dans le mauvais commit (test_admin_jobs_global.py dans le commit chore lint, 2026-07-19). Toujours des listes de fichiers explicites.
- [infra] Le sync `.env` de `dev-deploy.sh` n'écrase JAMAIS une clé existante : une valeur périmée (ex. `LOKI_URL` sur l'ancienne IP .116) survit à tous les redéploiements et fait pousser Alloy silencieusement dans le vide. Corriger la valeur À LA MAIN sur le serveur, jamais via .env.example. Garde ajoutée : ping Loki /ready en fin de dev-deploy (2026-07-20).
- [identité] Avant tout UPDATE d'owner_id basé sur sha256(email), VÉRIFIER que le hash cible = l'identité résolue par la session (GET /api/me/profile, ou hash d'un objet fraîchement créé via l'IHM). Un email mal orthographié (gaelgaeh5 vs gaelgael5) a envoyé les objets vers une identité fantôme — 3 allers-retours SQL pour le voir (2026-07-25).
